# 教科書の章の作り方（説明と問題が1対 → 章末の演習問題）

利用者はプログラミング未経験の初心者です。東京大学「Pythonプログラミング入門」（https://utokyo-ipp.github.io/）の各ページを、**省略せずに**、このアプリの教科書にします。
見本は **lib/learn/c1-1.ts（1-1 数値演算）** です。書く前に必ず全部読み、同じ細かさ・同じ調子で書いてください。

## 利用者から受けた指摘（これを守るための決まり）
- 「参照元は非常に分かりやすいが、こちらは1行説明で、説明のない問題がある」→ 参照元と同じ細かさで、**まず説明して知る**。1つの記号・考え方ごとに「短いコード → 結果 → 1〜3文の説明」。似たものは並べて違いを見せる（/ と //）。エラーになる例も見せる。
- 「インプットがないのにいきなりアウトプットはできない」→ **習っていないものを問題に出さない**（自動テストで確かめる）。
- 「学ぶ・読む・書くの違いが分からない。似た内容が並んでいる」→ 1本の流れにする。同じことを2回聞かない。
- 「説明と問題が離れると確認が手間」→ **説明と問題は1対**。1つの説明のまとまりの、すぐ下に、その説明だけを確かめる問題をちょうど1つ。
- 「演習問題は別章に」→ 章の最後の `exercises`（独立したページ）に、章の内容を組み合わせる問題を置く。
- 「アプリの説明と Python の説明が混ざっている」→ アプリの使い方は 1-0 だけ。ほかの章に「▶ 実行ボタン」などアプリの話を書かない。
- 「初めての人が説明だけを読んで 90点以上取れること」→ 問題は、すぐ上の説明だけで**確実に**答えが1つに決まること（「〜ことがある」程度の説明では選べない問題にしない）。

## 作るもの
担当の章ごとに **lib/learn/<ファイル>.ts** の `chapter` を埋めます（型は lib/learn/types.ts）。
```ts
export const chapter: LearnChapter = {
  ref: "2-2",
  sections: [
    { title: "参照元の節の見出し", blocks: [ {h}, {p}, {code, out}, ..., { try: "問題id" }, {h}, {p}, ..., { try: "問題id" } ] },
    ...
  ],
  exercises: ["問題id", ...], // 章末の演習問題(章の内容を組み合わせる)
};
```
- **sections**: 参照元の見出しの順に。参照元の節を省かない（小見出しも内容を落とさない）。参照元の「練習」は、同じことを学べる**別の問題に作り直して** exercises に入れる。
- **blocks**: 「説明のまとまり（h / p / code）→ `{ try: id }`」のくり返し。
  - 1つのまとまりは**1つの記号・考え方**にしぼる。2つあるなら、まとまりを分けてそれぞれに問題を置く。
  - まとまりの直後に問題をちょうど1つ。try が2つ続く・最後が説明で終わる、はだめ（テストで落ちる）。
  - 問題は、**直前の例を写すだけで解けないように**（数や形を変える）。でも、すぐ上の説明だけで答えが1つに決まること。
  - 専門用語は初出で言いかえる。です・ます調、やさしい日本語（c1-1.ts と同じ調子）。
- **{ code, out }**: out は実際の表示と完全に一致（最後の改行は除く）。エラーを見せる例は「エラーより前の出力 ＋ 改行 ＋ エラーの文」をそのまま out に書く（例は c1-1.ts の「エラー」の節）。乱数は seed を固定。
- **exercises**: 1問以上。章で習ったことだけを使う。

## 問題（try と exercises に入れる id）
- 問題の置き場所は今までと同じ:
  - 1-2, 1-3, 1-4, 2-1: 書く = lib/lessons.ts の ALL（と lib/extra.ts の EXTRA）、並び = lessons.ts の ORDER、読む = lib/reading.ts の BASE_READ。
  - 2-2 以降と付録: lib/chapters/<ファイル>.ts の lessons（書く・AI）/ reads（読む）/ order。
- **その章の既存の問題は、すべてどこかの try か exercises に入れる**か、不要なら消す（消すときは order からも消す）。同じ問題を2回使わない。
- 新しい問題の id は章ごとの接頭辞（例: 2-2 の読む `r22-...`、書く `l22-...`、付録 set は `rset-...` / `set-...`）。ほかの章と重ならないこと。
- 既存の問題の文・判定は、初心者に分かりやすく直してよい。判定（solution / expect / test / mustInclude / answer / choices）を変えたら、starter と wrong が不正解、solution が正解になることをテストで確かめる。
- 書く問題: 出力（test があれば test の出力）が expect と一致し、mustInclude の文字がすべてコードにあれば正解。課題文だけで何を表示すればよいか分かるように（表示する言葉を「」で囲むと、かぎかっこまで表示すると誤解されるので避ける）。mustInclude は正しい別解を落とさない最小限に。答えの数を直接 print しても通ってしまうなら、mustInclude に記号を入れる。input() は使えない。
- 読む問題: 3択。answer の位置は 0/1/2 をばらつかせる。正解の選択肢だけが実際の実行結果と一致すること。explain はやさしく、まちがえた人がどこで勘違いしたかも書く。読む問題のコードはエラーなしで動くこと（エラーになるかを問うときは書く問題で）。
- 古い仕組みの `topics` と `explain`（lib/chapters/<ファイル>.ts の topics / explain、base の章なら lib/topics.ts の BASE_TOPICS・lib/explain.ts の BASE_EXPLAIN の該当章）は、もう画面に出ません。**担当の章の分は空にしてください**（古い「省略なし」「説明の量」テストの対象から外れます）。refSections / refProse は変えない。
- 書く問題の `intro` / `example` も画面に出ません（説明は教科書に書く）。

## このアプリでできないこと
- ファイル（4-1、付録 CSV）・ディレクトリ（4-3）・モジュールの作成（5-2）: ブラウザの中の仮のファイル置き場で open() や os が使える。問題の中で先にファイルを書いてから読む形にする。前の実行のファイルが残ることがあるので、毎回作り直すコードにする。
- コマンドライン（付録）: 実際には動かせない。説明と、sys.argv を仮に作って読むような問題で扱う。
- Jupyter / Colab の使い方（付録 Jupyter）: アプリの使い方は 1-0 に2項目だけ。付録 Jupyter の章は作らない（lib/learn に置かない。lib/chapters/a-jupyter.ts の lessons / reads / order / topics / explain は空にする）。
- グラフ（付録の可視化・Matplotlib・Bokeh、5-3 など）: matplotlib の図は結果の下に画像で出る。グラフの中の文字は英語（日本語の文字は出ない）。問題の判定は test で図の中身を print して確かめる。Bokeh は使えないので「Bokeh ではこう書く」と説明し、問題は同じ種類のグラフを matplotlib で。
- AI の章（5-3, 7-1, 7-2）は numpy / pandas / scikit-learn が使える。

```
npx tsc --noEmit -p .
npx eslint app lib

node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON scripts/check-similarity.mts
node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON scripts/exam.mts export <章> <出力.md>   # 答えを伏せた試験(初めての人に渡す)
```
tests/learn.test.mts が確かめること: 1対の並び / 章末の演習問題 / 章の全問題がどこかに入っている / 重複なし / **問題のコードに出てくる記号・関数・メソッド・引数名・文法の言葉が、その問題より上の説明（h と p の文章）に、その文字のまま書かれている**（前の章の説明も含む。lib/learn/terms.ts）/ 例の結果の一致。
テストを弱めたり消したりしない。app/ と tests/ と lib/learn/terms.ts・types.ts・index.ts は変えない。
